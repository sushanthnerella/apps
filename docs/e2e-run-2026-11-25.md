## Bugs found

1. **Priest Schedule shows "Could not load availability. Please retry." whenever a date has no slots.**
   `GET /api/v1/priests/slots?priest_id=…&date=2026-11-26` returns HTTP 200 with body `null` instead of `[]`. The app parses `List<PriestSlotPayload>` and fails. Fix in the backend handler (`backend/cmd/api-gateway/slot_routes.go`): return an empty slice, not nil. Check other list endpoints for the same nil-slice pattern.
2. **Service matching (from earlier investigation).** `priests.services_offered` is fixed at signup (`backend/internal/db/db.go:583`) and "My Offerings" never updates it, so CMS services with other names never find a priest.
3. **Completion-code dialog keeps the previous wrong code.** After "Incorrect code", reopening "4. Complete" shows the old code (e.g. 1234) in the field; the field length limit stops the priest typing the right code until they delete it.
4. **No feedback after "Update my location"** on the priest Duty Radar. The location is saved (backend confirms) but nothing tells the priest.
5. **Decline may not reach the devotee promptly** (C9 above). Needs a re-check: devotee should see "The priest declined…".
6. **Devotee app showed an "Unable to load booking" dialog on launch** while the emulator had no network and the user was on the login screen. A logged-out user should not see a booking error.
7. **Payment:** no Razorpay or any gateway in backend or apps; all copy says "No online payment is collected".
8. **Firebase:** `google-services.json` missing for devotee and priest apps; `GoogleService-Info.plist` missing for iOS; backend needs `FCM_SERVICE_ACCOUNT_JSON`.

### New bugs (second pass)

9. **Priest decline never reaches the server.** `PriestApp.kt` ~line 600: `onReject` launches a coroutine that reads `activeBookingId`, then immediately sets `activeBookingId = ""`. The coroutine runs after the reset and sends an empty booking ID. Capture the ID in a local `val` before launching (the Accept path should be checked for the same pattern).
10. **Priest app crash loop: `DutyLocationService` restarted from background.** After the app is force-stopped while on duty, Android restarts the sticky service; `startForeground(..., FOREGROUND_SERVICE_TYPE_LOCATION)` at `DutyLocationService.kt:39` throws `SecurityException` (location FGS not allowed from background, targetSDK 34). Result: "Puja Vaahini Purohit keeps stopping". Return `START_NOT_STICKY` and guard `startForeground` with try/catch + `stopSelf()`. This file has uncommitted changes. High priority — real phones kill background apps often.
11. **Normal (home-visit) requests never expire on the server.** The expiry sweep (`backend/internal/db/event_ops.go:607`) only covers `event_id IS NOT NULL`. The priest alert times out locally after ~30 s and just hides. Add expiry for normal requests (and release the slot hold).
12. **Expiry message wording.** Devotee sees "This request was cancelled." for an expired ghat request; should say it expired and nothing is owed.
13. **Overlapping ghat request accepted from the devotee.** Backend blocks the priest accept (409), but the devotee is not told the priest is busy at that time and the request sits until expiry.
14. **Cancel API says "100% Instant Refund" and `escrow_status: REFUNDED_TO_DEVOTEE`** although no payment exists. Must be real once Razorpay is added.
15. **After accepting from the Pushkaralu tab, the alert closes and nothing on that tab shows the booking**; the priest has to go to Duty Radar.

### New bugs (third pass)

16. **Temple VIP pujas never load.** `TempleVipPuja` in `apps/common-contracts/.../temple/TempleModels.kt` uses camelCase fields (`templeId`, `maxDailySlots`, `durationMinutes`, `isOnlineVideoCall`, `isActive`) with no `@SerialName`, while the API sends snake_case (`temple_id`, …). `templeId` is required, so parsing fails. Add `@SerialName` or a snake_case naming strategy. Check the other models in that file.
17. **Staging email not configured.** Set `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `EMAIL_VERIFICATION_BASE_URL` and `PASSWORD_RESET_BASE_URL` on Render.

19. **Devotee location-denied message is wrong.** Say that location permission is off, offer "Open settings", and let the devotee continue with a typed address.
