1. CORE PARTICIPATING ACTORS
----------------------------------------------------------------------------------------------------
1.1 Devotee (Ghar Ka Yajamana / Pilgrim / VIP):
    - Multi-language selection: English, Telugu (తెలుగు), or Hindi (हिन्दी).
    - Profile with Profile Picture upload, Gotram, Nakshatram, Rashi, City.
    - Books home poojas, temple-specific VIP pujas, and live temple E-Pooja video calls (WebRTC).
    - Selects priest slots, views required material checklist before ordering.
    - If material kit is unchecked, purchases directly from local vendors via integrated "Puja Store".
    - Two-way in-app real-time chat with the assigned priest.
    - Swiggy-style cancellation flow with refund transparency and retention rescue hooks.
    - Protected back navigation and clear logout modal.

1.2 Vedic Priest (Purohit / Ayagaryllu):
    - Language selection (English, Telugu, Hindi) with native Vedic terminology.
    - Profile with Profile Picture, Vedic Shakha, Sampradaya, and Experience.
    - Configures available calendar slots (date/time windows).
    - Adds custom pooja services with personalized Dakshina pricing.
    - Edits/tailors the required Samagri material checklist per booking.
    - Peer Referral: Instantly auto-reassigns/delegates a booking to a known colleague priest with immediate devotee notification.
    - Two-way in-app real-time chat with devotee.
    - Conducts live in-person or temple WebRTC live video calls.
    - Duty toggle and protected logout flow to prevent accidental duty disconnection.

1.3 Local Pooja Store Vendor:
    - Operates via a dedicated "Vendor App" (Compose Multiplatform Android).
    - Multi-language support for regional inventory management.
    - Profile with Profile Picture, Store Name, Geolocation, and Contact info.
    - Manages inventory (fresh pooja flowers, brass diyas, pure cow ghee, havan samagri).
    - Receives, packs, and delivers orders when devotees arrange materials independently.

1.4 Temple Administrator & Counter Clerk:
    - Operates via a dedicated "Temple CMS" (Next.js / React Web Portal).
    - Manages temple profiles (e.g., Dhapurmari Temple, Kotipalli, Vemulawada), deities, timings.
    - Configures Temple-specific VIP Pujas, VIP Ticket slots, and Live E-Pooja Video streaming slots.
    - Assigns Temple Archakas/Priests and manages revenue collection/reconciliation without lag.
    - Operates ultra-fast counter check-in scanner (< 50ms, offline-resilient).

====================================================================================================
MODULE A: PRIEST CALENDAR SLOTS, CUSTOM SERVICES & DAKSHINA PRICING
====================================================================================================

UC-A01: Priest Calendar Slot Availability Management
    - Actor: Priest
    - Flow:
      1. Priest opens "Schedule Workbench".
      2. Selects date and marks hourly availability slots (e.g., Morning: 06:00-09:00, 09:30-12:30; Evening: 17:00-20:00).
      3. Sets recurring rules or blocks specific dates for personal rituals.
      4. Slots are stored in PostgreSQL (`priest_availability_slots`) and cached in Redis.

UC-A02: Priest Adds Custom Rituals & Personalized Pricing
    - Actor: Priest
    - Flow:
      1. Priest opens "My Services" in Priest App.
      2. Creates a custom pooja (e.g., "Navagraha Homa + Dhanvantari Homa Special").
      3. Sets base Dakshina fee, estimated duration, and samagri requirements.
      4. Devotees searching for nearby priests can see and book these custom offerings directly.

UC-A03: Devotee Slot Booking & 10-Minute Hold Lock
    - Actor: Devotee
    - Flow:
      1. Devotee selects a priest and pooja package.
      2. Devotee views available green slots for that priest.
      3. Devotee selects matching slot -> slot temporarily locks for 10 minutes in Redis via Redlock pending checkout confirmation.

====================================================================================================
MODULE B: EDITABLE SAMAGRI (MATERIAL) CHECKLIST & PUJA STORE WITH VENDOR APP
====================================================================================================

UC-B01: Devotee Pre-Order Material Checklist Inspection
    - Actor: Devotee
    - Flow:
      1. Devotee views pooja package details.
      2. Devotee taps "View Required Samagri List".
      3. Complete categorized list is displayed:
         - Fresh items (Betel leaves, Mango leaves, Coconuts, Flowers, Fruits)
         - Dry essentials (Turmeric, Kumkum, Akshata, Camphor, Dhoop, Pure Ghee, Dry fruits)
         - Havan items (Havan samagri, Navadhanya, Sacred firewood)
      4. Checkbox option:
         [X] "Priest brings complete Samagri Kit" (Default: checked, e.g. +Rs. 1,200)
         [ ] "I will arrange my own materials"

UC-B02: Priest Customizes & Edits Samagri List per Booking
    - Actor: Priest
    - Flow:
      1. Priest views custom pooja service or incoming booking.
      2. Priest edits the items/quantities based on specific family tradition or gotram.
      3. Priest saves updated checklist, which dynamically syncs to Devotee app.

UC-B03: Devotee Unchecks Samagri -> Redirected to Puja Store
    - Actor: Devotee, Local Vendor
    - Flow:
      1. Devotee unchecks "Priest brings complete Samagri Kit".
      2. App presents option: "Would you like local vendors to deliver fresh Samagri to your doorstep? [Visit Puja Store]".
      3. Devotee enters "Puja Store" with pre-filled shopping list containing the missing items.
      4. Devotee sees nearby verified vendors ranked by proximity and rating.

UC-B04: Puja Store Order Placement & Doorstep Delivery
    - Actor: Devotee, Local Vendor
    - Flow:
      1. Devotee reviews cart with pre-populated samagri kit from local vendor.
      2. Devotee confirms delivery address and selects delivery slot.
      3. Payment processed; order routed to the nearest vendor via Vendor App.

UC-B05: Dedicated Vendor App Operations (Compose Multiplatform Android)
    - Actor: Local Vendor
    - Flow:
      1. Local vendor signs up, adds shop name, address, profile pic, and phone number.
      2. Vendor updates catalog prices and stock availability.
      3. Vendor receives sound alert for new samagri orders.
      4. Vendor accepts order, marks "Packed" and "Dispatched/Delivered".

====================================================================================================

UC-D01: Priest Peer Delegation with Instant Reassignment

      2. Priest opens active booking and taps "Refer to Colleague".
      3. Priest selects a trusted, verified purohit from their contact network.
      4. System performs Instant Auto-Reassignment:
         - Booking is immediately reassigned to the referred priest (`bookings.priest_id = referred_priest_id`).
         - Escrow funds and booking schedule remain intact.

UC-D02: Devotee Instant Notification & Transparent Profile Card
    - Actor: Devotee
    - Flow:
      1. Push notification & in-app banner sent to Devotee:

      2. Devotee views referred priest's profile picture, Vedic qualifications, and phone number.
      3. Chat thread automatically transfers to the new priest.

MODULE G: SWIGGY / RAPIDO STYLE CANCELLATION MODAL & REFUND POLICY
====================================================================================================

UC-G01: Devotee Cancellation Flow with Retention & Refund Breakdown
    - Actor: Devotee, Backend Escrow Engine
    - Trigger: Devotee taps "Cancel Booking" on Live Tracking or Booking Details screen.
    - Flow:
      1. System opens interactive Cancellation Bottom Sheet / Modal:
         a) Warning Header: "Are you sure you want to cancel?"
         b) Status Indicator:
            - If in `REQUESTED` stage: "100% Instant Refund - Free Cancellation"
            - If in `ACCEPTED` stage (within 5 mins): "100% Instant Refund - Priest hasn't departed yet"
            - If in `IN_TRANSIT` stage: "Priest is on the way (ETA: X mins). Nominal travel allowance (Rs. 150) applies, remainder refunded instantly."
         c) Retention Hook: "Need to change timing? You can reschedule or reassign to another purohit for free!"
            - Button: [Reschedule / Reassign Instead]
         d) Reason Selector (Mandatory single-select with write-in):
            - [ ] Priest taking too long / unresponsive
            - [ ] Change of family plans / postponed muhurtham
            - [ ] Arranged alternate purohit locally
            - [ ] Selected wrong pooja / incorrect date
            - [ ] Other (User text input)
         e) Refund Summary Box:
            - Advance Dakshina Paid: Rs. X,XXX
            - Cancellation Fee: Rs. 0 (or Rs. 150 if priest arrived)
            - Total Refund to Original Source: Rs. X,XXX
      2. Devotee confirms via "Swipe to Cancel" or [Confirm Cancellation] button.
      3. Backend updates booking status = `CANCELLED`, cancelled_by = `devotee`, escrow_status = `REFUNDED_TO_DEVOTEE`.
      4. Priest receives instant push alert: "Booking cancelled by devotee. Travel allowance credited to wallet."

UC-G02: Priest Cancellation & Automatic Devotee Rescue
    - Actor: Priest, Backend Dispatch Engine, Devotee
    - Trigger: Priest taps "Unable to Attend / Cancel Duty".
    - Flow:
      1. Priest selects reason (exigency, vehicle breakdown, emergency).
      2. System prompts Priest: "Would you like to refer this booking to a known colleague?"
         - Option A: Priest selects colleague -> triggers UC-D01 (Instant Reassignment).
         - Option B: Priest taps "No, Re-Dispatch" -> Backend returns booking to `REQUESTED` state and notifies next highest-ranked priest within the search radius.
      3. Devotee screen displays gentle banner: "Your priest encountered an emergency. We are connecting you to an equally qualified nearby Purohit immediately."

UC-G03: 45-Second Dispatch Timeout & Auto-Escalation
    - Actor: Dispatch Engine
    - Flow:
      1. Dispatch request sent to highest-scoring priest on radar with 45-second countdown timer.
      2. If timer expires without priest response, system auto-escalates to candidate #2 on radar.
      3. Devotee app maintains pulsing radar animation without dropping connection.

MODULE I: UX RESILIENCE, BACK-NAVIGATION GUARDS, LOGOUT MODAL & NETWORK ERROR STATES
====================================================================================================

UC-I01: Hardware & System Back-Navigation Guards
    - Context: Android system back gesture / back button press (`BackHandler`).
    - Flow Rules:
      1. Root Tabs: First back press triggers snackbar "Press back again to exit". Second press within 2s closes app.
      2. Sub-Screens: Regular back press cleanly navigates up to parent tab.
      3. Protected Critical States:
         - Checkout / Slot Reserve: Intercepts with "Leaving will release reserved slot. Discard? [Stay / Discard]".
         - Live WebRTC Sankalpam: Options for [Minimize to Background Audio (PiP)] or [End Video Call].
         - In-Transit Tracking: Returns to Home tab with persistent top banner showing active ETA.

UC-I02: Logout Confirmation Popup & Session Purge
    - Trigger: User taps "Log Out" on Profile screen.
    - Flow:
      1. Displays styled confirmation dialog: "Log Out of Puja Vaahini? You will need to re-verify via OTP."
      2. Active Order Guard: Displays warning if pooja is in-progress: "⚠️ Active pooja scheduled. Logging out will NOT cancel the ritual."
      3. Confirm action clears JWT tokens, disconnects WebSockets/WebRTC sessions, purges backstack (`popUpTo(0)`), and routes to Login screen.

UC-I03: Loading Skeletons & Animated Shimmers
    - Shimmer skeletons for Catalog grid, Nearby Priests radar list, Temple directory, and Puja Store products.
    - Contextual loaders for Radar scanning, Escrow locking, and Muhurtham verification.

UC-I04: Network Disconnection & Offline Error States
    - Native network monitor displays top amber bar: "⚠️ No Internet Connection. Showing offline cached details."
    - Full-Screen `NetworkErrorScreen` with sacred disconnected illustration and `[🔄 Try Again]` exponential backoff retry.
    - 500 Server Maintenance View: "Our servers are undergoing routine Vedic ephemeris synchronization. We will be back online shortly."

UC-I05: Empty Search States & Radius Expansion
    - Trigger: Devotee searches with specific Sampradaya or category where 0 priests match.
    - View: Displays empty state illustration with spiritual copy: "No Purohits found matching your criteria within 5 km."
    - Action: Primary button [Expand Search Radius to 15 km].

MODULE J: 3-LANGUAGE INTERNATIONALIZATION (i18n) & MODULAR LOCALIZATION ARCHITECTURE
====================================================================================================

UC-J01: Language Selection & Live App Re-Rendering
    - Supported Languages:
      1. English (`en`) - Default / Urban & Diaspora Devotees
      2. Telugu (`te` - తెలుగు) - Primary regional language for Vedic Purohits & South shrines
      3. Hindi (`hi` - हिन्दी) - Pan-Indian / North Indian Vedic rituals & devotees
    - Trigger Points:
      1. First App Launch: Language selection welcome screen with native language cards (English, తెలుగు, हिन्दी).
      2. Profile Settings: 1-click Language Switcher radio bottom-sheet accessible at any time.
    - Flow:
      1. User selects language.
      2. `LocalizationManager` updates active `AppLanguage` state.
      3. Compose `CompositionLocalProvider(LocalAppStrings provides localizedStrings)` triggers zero-reboot instant UI re-render across all active screens.
      4. Selection is saved to local encrypted preferences and synced to backend (`users.preferred_language`).
      5. Backend sends future Push Notifications and SMS OTPs in the selected language.

UC-J02: Modular Clean-Architecture i18n Folder Organization
    - Structure located in shared common contracts for 100% code reuse across Devotee, Priest, and Vendor apps:
      `apps/common-contracts/src/commonMain/kotlin/com/purohit/contracts/i18n/`
    - Domain-partitioned string interfaces to prevent monolithic, unmaintainable string files:
      ├── `AppLanguage.kt` (Enum with ISO code, native script name, and script direction)
      ├── `LocalizationManager.kt` (State manager, preference loader, and Compose Local provider)
      ├── `StringContract.kt` (Aggregator interface matching all sub-domain contracts)
      ├── `models/` (Type-safe domain contracts):
      │   ├── `AuthStrings.kt` (Login, OTP, KYC, Gotram, Consent agreements)
      │   ├── `CatalogStrings.kt` (Pooja titles, Muhurtham labels, categories, durations)
      │   ├── `SamagriStrings.kt` (Checklist, items, dry/fresh categories, Puja store)
      │   ├── `DispatchStrings.kt` (Radar, ETA, ratings, transit status, OTP release)
      │   ├── `TempleStrings.kt` (Sanctum, VIP passes, E-Pooja video call, deities)
      │   ├── `CancellationStrings.kt` (Swiggy-style reasons, refund warnings, retention)
      │   └── `ErrorStrings.kt` (Offline alerts, retry buttons, maintenance notices)
      └── `locales/` (Pure language implementations):
          ├── `en/` (English modular classes)
          ├── `te/` (Telugu / తెలుగు modular classes)
          └── `hi/` (Hindi / हिन्दी modular classes)

UC-J03: CompositionLocal Reactive Zero-Reboot Live Re-Rendering
    - Flow:
      1. Entire UI tree is wrapped in `CompositionLocalProvider(LocalAppStrings provides currentStrings)`.
      2. Any UI element referencing `LocalAppStrings.current.catalog.satyanarayana` updates instantaneously upon state change without Activity restart.

UC-J04: Backend Language Header Sync (Accept-Language)
    - Flow:
      1. Every outgoing HTTP request appends `Accept-Language: te` (or `en`, `hi`).
      2. Backend extracts header and localized error payloads, SMS OTP text, and WhatsApp notifications accordingly.
